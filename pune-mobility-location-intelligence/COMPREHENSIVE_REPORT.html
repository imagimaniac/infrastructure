1. Executive Summary

This project demonstrates a data-driven approach to quantifying how traffic accessibility impacts real estate value in Pune. It bridges traffic microsimulation (Eclipse SUMO + TraCI) with location economics to produce developer-focused ROI insights. The core hypothesis: reducing junction-level wait times improves accessibility, creating a measurable location premium that translates to developer ROI.

Key Takeaway: The differentiation lies in the lens (Mobility → Accessibility → Location Premium → Developer ROI) and rigorous traceability (every assumption tagged Assumed/Cited/Derived with URLs and retrieval dates).

2. Problem Statement & Strategic Differentiator

2.1 Problem Statement

Pune faces persistent peak-hour congestion across IT corridors (Wakad–Tathawade–Hinjewadi, Kharadi). While traffic studies report mobility KPIs and real estate studies cite location factors, these domains rarely connect quantitatively. Developers need defensible numbers linking accessibility improvements to business value.

2.2 Strategic Differentiator

Unlike generic traffic dashboards, this POC treats accessibility gain as location intelligence. It maps operational improvements to developer-relevant outcomes (absorption support, price/rental lift potential, realizations) with explicit sensitivity ranges.

3. Conceptual Framework & Value Chain

The project follows a four-layer value chain that explicitly connects engineering outputs to business outcomes.

Figure 1: Value Chain - Mobility → Accessibility → Location Premium → Developer ROI

Mobility → Accessibility

Microsimulation compares Fixed-Time vs Max-Pressure control. KPIs: avg wait, queue length, travel time, stops, throughput, fuel/emissions.

Accessibility → Location Premium

Parameterized elasticity ranges (0.05–0.40% per 1% wait reduction). Marked as directional hypothesis with sensitivity analysis.

Location Premium → Developer ROI

Translates to price/rental lift potential, absorption support, and monetized savings (VoT + Fuel + Emissions).

7. Methodology, KPIs & Formulas

7.1 Control Strategies

  • Baseline: Fixed-time signal control (deterministic comparison)
  • Adaptive: Max-Pressure - selects phase with highest pressure P_p = (inbound halting queues) - (outbound queues/capacity)

7.2 Key Performance Indicators

KPIDefinitionPurpose
Avg Wait Time (s/veh)Avg stopped timeCore accessibility proxy
Queue Length (veh)Halting vehiclesBottleneck indicator
Travel Time (s/trip)Trip durationNetwork performance
Stops (avg)Stop eventsReliability
Throughput (veh/hr)Completed tripsCapacity
Fuel (L), CO2e (kg)Consumption/emissionsCost + ESG

7.3 Core Formulas

  • % Reduction: (W_fixed - W_adapt)/W_fixed × 100
  • VoT Saved: Δt_wait_hr × Vehicles_affected × VoT_INR/hr
  • Fuel Saved: ΔFuel_L × FuelPrice_INR/L
  • Emissions Saved: ΔCO2e_kg × SocialCost_INR/kg (social cost, separate)
  • Accessibility→Premium (directional): ΔPrice% ∈ [ε_low, ε_high] × (% wait reduction), ε ∈ [0.05, 0.40]

11. Reproducibility Guide

11.1 Quick Start (Demo - works without SUMO)

cd ~/Projects/infrastructure/pune-mobility-location-intelligence
.venv/bin/streamlit run scripts/dashboard.py

11.2 Full Simulation (with SUMO + TraCI)

cd ~/Projects/infrastructure/pune-mobility-location-intelligence
source .venv/bin/activate
pip install -r requirements.txt
pip install traci sumolib  # if needed
# Ensure SUMO binary available; set SUMO_HOME if required
python scripts/generate_synthetic.py
python scripts/baseline_fixed.py
python scripts/adaptive_pressure.py
streamlit run scripts/dashboard.py

Note: If SUMO binary missing, use scripts/run_offline_demo.py to regenerate demo CSVs.

13. Limitations, Risks & Next Steps

13.1 Limitations

  • Currently uses synthetic network/demand (demo) — not full Pune GIS calibrated with real counts
  • Accessibility elasticity is directional (literature gap) — always presented as ranges
  • Junction-level control focus (network-wide effects not fully modeled)
  • Fuel/emissions depend on SUMO model availability

13.2 Mitigations

  • Explicit Assumed/Cited/Derived tagging; sensitivity analysis
  • Conservative defaults, bounded ranges
  • Separation of cash (VoT+Fuel) vs social (emissions) in reporting
  • Full reproducibility and traceability

13.3 Next Steps

  1. Model real corridor (OSM slice) for Wakad–Hinjewadi/Tathawade
  2. Calibrate with plausible demand; run with SUMO binary
  3. Refine max-pressure implementation (phase constraints, min/max green)
  4. Validate elasticity references if available; document uncertainty
  5. Add route/corridor visualizations for stronger pitch
